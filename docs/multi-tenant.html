一、业界对标：六个 Agent SaaS 平台的多租户做法（2026-08-30 检索核实）

前提修正（龙哥拍板）：未来 DSH 是服务器部署、登录或授权后才能使用的形态——「用户」不再是可选层，而是一切能力的第一维。未认证请求一律拒绝（fail-closed），不再有匿名模式；本地 CLI 单机形态作为特例（uid=local）保留兼容。

1.2 业界通用规律（多篇生产实践总结）

  1. 严禁多用户共用 Agent 运行实例——一用户（至少一会话）一隔离实例，实例间状态零共享；共享只发生在数据层（带归属过滤）。
  2. 身份来自认证层，绝不来自客户端自报——thread_id / session_id 由服务端从身份派生或登记，客户端自报 ID 会造成越权与历史丢失。
  3. 租户过滤必须收敛到单点 + 数据库兜底——应用层靠「所有查询过同一个上下文过滤器」（Dify 的装饰器 / 方案的 sessionQuery 可见集），数据库层靠 RLS（LangGraph）做最后防线，防「有人写 SQL 手滑漏了 tenant_id」。
  4. 凭证隔离到用户/租户级——Dify 每租户独立密钥、WorkBuddy 连接器按用户授权；全局明文凭证（现状 .credentials.yaml）在多租户下是高危项。
  5. 控制平面四件套：超时、并发上限、配额、审计——Manus / Dify 均在网关/中间件层强制执行，不依赖 Agent 自觉。
  6. 大文件走对象存储，不进 OLTP——会话日志、导出物、附件按桶/前缀放文件系统或对象存储，数据库只存元数据与索引（dsh 现状 jsonl+zstd + storages 元数据天然符合）。

关键机制：请求级用户上下文怎么注入

dsh 所有客户端调用都过 apiproxy（webserver:3080）。改造方式：

  1. 在 apiproxy 前加强制认证中间件（fail-closed：解析不出身份 = 直接 401，绝无匿名兜底），解析出 userId / tenantId；

十、插件管理与插件设置的分级设计（2026-08-30 增补）

技能（SKILL.md）是内容层，插件（Cordis package）是代码层——前者只是文本注入，后者在进程内全权限执行。两者的分级模型必须分开设计。先看源码现状：

10.1 现状盘点：dsh 的插件与设置机制（源码核实）

机制现状实现多用户缺口
插件组装profile = 具名组装：bundle 顺序 → profile cordis.patch.yml → home 级 patch → --patch overlay，四层叠加按 id 替换/插入行；dsh --dump-config 可审查profile 与 patch 全落 DSH_HOME，home 即单用户，无系统/用户之分
插件安装dsh plugin CLI 把树外插件装进 profile 的 node_modules + patch 条目装进的是「这台机器的 home」，无归属、无审批、无版本治理

10.5 登记表与验收

安装准入与租户策略需要落 PG（加入第十四节数据模型）：

-- 插件登记（准入审计，非启用关系——启用关系在用户 patch 文件里）
CREATE TABLE plugin (
  plugin_id     TEXT PRIMARY KEY,        -- npm 包名或内部 id
  scope_type    TEXT NOT NULL CHECK (scope_type IN ('system','tenant','user')),
  tenant_id     TEXT REFERENCES tenant(tenant_id),  -- system 级为 NULL
  owner_user_id TEXT REFERENCES app_user(user_id),     -- 安装发起人
  version       TEXT NOT NULL,
  status        TEXT NOT NULL,           -- approved | pending | rejected
  manifest_hash TEXT NOT NULL,           -- 安装包指纹（防替换）
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- 租户设置策略（L2）
CREATE TABLE plugin_policy (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id    TEXT NOT NULL REFERENCES tenant(tenant_id),
  plugin_id    TEXT NOT NULL,
  ns           TEXT NOT NULL,            -- settings 命名空间
  field_path   TEXT NOT NULL,            -- 字段路径（支持点号嵌套）
  policy_type  TEXT NOT NULL CHECK (policy_type IN ('force','lock')),
  value        JSONB,                    -- force 时的强制值
  PRIMARY KEY (tenant_id, plugin_id, ns, field_path)
);

验收用例（4 条）：① 用户 patch 引用未准入插件 → 启动被拒；② 租户 lock 某字段 → 用户改 settings.yaml 无效且 UI 灰掉；③ 租户 force 禁遥测 → 所有用户 describe() 该字段只读；④ 用户 A 安装（白名单内）插件 → 用户 B 的 dump-config 无此行。

-- ============ RLS 行级安全兜底（服务器模式必开）============
-- 连接层：每个请求开始时 SET LOCAL（事务级，连接归还池自动失效）
--   SET LOCAL dsh.tenant = '<tenantId>';  SET LOCAL dsh.uid = '<userId>';
ALTER TABLE session_meta ENABLE ROW LEVEL SECURITY;
CREATE POLICY p_session_meta_rw ON session_meta
  USING (
    tenant_id = current_setting('dsh.tenant')::uuid
    AND (
      user_id = current_setting('dsh.uid')::uuid          -- 自己的
      OR workspace_id IN (                                 -- 共享工作区成员的
           SELECT workspace_id FROM workspace_member
           WHERE user_id = current_setting('dsh.uid')::uuid)
      OR EXISTS (SELECT 1 FROM session_share s          -- 被显式授权的
           WHERE s.session_id = session_meta.session_id
             AND s.grantee_type = 'user'
             AND s.grantee_id = current_setting('dsh.uid')::uuid)
    )
  );
ALTER TABLE memory ENABLE ROW LEVEL SECURITY;
CREATE POLICY p_memory_rw ON memory
  USING ( (scope_type='user'  AND scope_id = current_setting('dsh.uid')::uuid)
       OR (scope_type='tenant' AND scope_id = current_setting('dsh.tenant')::uuid) );
-- workspace / workspace_member / session_share 同理挂 tenant 边界策略
-- 注意：dsh 服务连接用非超级用户角色（RLS 对表 owner/超级用户默认不生效），并 REVOKE 直连权限
PG 化要点说明
RLS 生效前提服务账号必须是非表 owner 的普通角色，否则策略被绕过；每请求 SET LOCAL 绑定在事务内，连接池归还即失效，不会串号
TEXT vs UUIDsession_id 保持 TEXT（兼容现有 uuid 字符串，避免全量改型）；人/租户/工作区等新实体一律 UUID
时间类型TIMESTAMPTZ 统一带时区——服务器多用户跨时区/审计必备，SQLite 的 TEXT 时间无法比较排序
本地 CLI 降级uid=local 时 storage-postgres 不装配，回落 jsonl+sqlite（现状），不要求本地装 PG
迁移dsh migrate multiuser 附带 --to-postgres：本地 SQLite 数据导入 PG（单用户试点升服务器时用）

对应测试数据脚本要点（下一步可单独出，PG 版）：1 租户 2 用户、3 工作区（1 私有 + 1 共享 + 1 无关用户私有）、5 会话（含 1 条 fork 血缘）、2 条 share（read/fork 各一）、L3/L4 记忆各 2 条、附件/导出物各 1 条——足够覆盖全部权限矩阵用例；另加 3 条 RLS 负向用例（跨租户读、跨用户读、过期 share 读均应 0 行）。

十九、树外开发与官方升级策略（2026-08-30 增补：零 fork 目标）

回答核心问题：整体开发必须以插件（树外）方式开发，目标是零 fork。fork 官方仓库 = 每次 release 都要 rebase 16 个包的改动、解冲突、重新验证——成本随官方迭代频率线性增长，不可持续。而 dsh 的架构哲学恰好站在我们这边（源码原文）：

「There is no privileged core to patch: you extend dsh by mounting a plugin beside the others… including the model adapter, the tool registry, the session log, and the agent loop itself, so each is replaceable from configuration.」——没有特权内核，一切可从配置替换。这是 Cordis 插件体系的官方承诺，多用户改造可以整体住在树外。已有先例：dsh-uai-brand 品牌插件（client.js + cordis.patch.yml，零改官方源码）已验证这条路。

19.1 18 个改动点重分类：A 树外新插件 / B patch 配置替换 / C 上游依赖

类含义升级冲突面改动点
A：树外新插件独立仓库新建 Cordis 包，通过 patch insert 挂载零代码冲突。仅剩服务契约风险（上游改 ctx 接口 → 启动期 Requires 检查发现，比 git 冲突好解一个数量级）#1 host/auth、#2 multiuser-context、#5 session-query 可见集包装、#9 memory 域、#10 session-share、#15 插件准入、#17 host/lookup（v2026-09-06 增）、审计/指标/追踪（18.5）
B：patch 替换配置不改官方包代码，用 cordis.patch.yml replace 行换掉默认后端/参数（Cordis 注册是可逆 effect，卸载即还原）零代码冲突。冲突面收窄为：行 id 改名、config 字段名变更——loader-smoke 冒烟 3 分钟暴露#3 attachment/spill 根目录（replace 行 + config 传用户桶路径）、#4 会话持久化（replace 成 mu 包装后端，包装官方 jsonl 后端 + 归属列）、#6 skill roots（replace 配置）、#7 workspace 注册表（replace 成 PG 后端实现同一契约）、#8 settings 文档路径（replace settings-file 行，config 指向用户桶）、#11 导出落盘、#16 describe 扩展（见 C 类说明）、#12 凭证（replace credentials 行）、#18 storage-postgres DDL 增量（v2026-09-06 增，ALTER TABLE 加 biz_key / status / privacy 列 + UNIQUE 索引，migrations/0003_biz_key.sql）
C：依赖上游需要官方包新增接缝才能优雅实现无法完全消除，用「包装 + 启动器」规避到最少仅 2 项残留：① settings 租户策略层（官方只有 3 层解析）→ 规避：mu-settings 插件在 L3 用户层之上再包一层（A 类包装，不改 settings 包）；② profile 挪用户桶（app-boot 是启动器）→ 规避：自有 dsh-server 启动器（我们自己的 CLI 包装，按登录用户动态生成 patch 序列调 dsh --patch，app-boot 一行不改）
D：CLI 工具独立命令，与官方 CLI 并存无冲突#13/#14 dsh migrate multiuser、--to-postgres
结论：18 项里 0 项必须改官方包源码（v2026-09-06 增：#17 host/lookup 是新插件、#18 是 PG 增量迁移，均落在树外仓库或 storage-postgres 包内）。原方案标注「修改」的项，全部重新表述为「replace 配置行 + 树外包装插件」——这正是本次增补对第十节清单的修订。

19.3 官方升级工作流（每次 release 的固定动作）

步骤动作失败的处置
1. 锁版本 bumppackage.json 钉死官方 tag（禁止 latest 浮动）—
2. 冒烟（3 分钟）loader-smoke boot「官方 profile + mu-server.patch.yml」挂 = 行 id/config 字段变更（B 类冲突）→ 比对官方 --dump-config diff，更新 patch，通常 10 分钟内
3. 契约检查mu 包 inject 的官方服务接口类型编译 + Requires 声明校验挂 = A 类契约变更 → 看官方 .agents/notes/ 变更说明，包一层适配器；破坏性变更时评估锁老版本一版
4. 快照双跑mu-off 对官方基线（字节级一致）+ mu-on 全量场景off 挂 = 官方自身行为变化，与 mu 无关，记录基线更新；on 挂 = mu 回归，修复后才能升级
5. 负向安全N1–N6 全绿任何一条红 = 安全回归，禁止上线，最高优先级修复
6. 真实 API e2e双用户并发 + 配额触发（带 Key）人工分析

升级成本模型：fork 方案的冲突面 = 16 包 × 每处改动的代码行（随官方重构放大）；树外方案的冲突面 = 固定三类信号（patch 行失效 / 服务契约变更 / 快照基线漂移），且全部在 CI 里有独立红灯，定位精确。日常升级大概率只走到第 2 步就绿了。

19.4 与上游的双向关系（长期成本递减）

动作说明
订阅变更官方 .agents/notes/ 目录是结构化变更日志（架构/特性/修复分类），每次升级先读 notes 再看 diff——官方自己维护的升级指南
向上游提 PRB/C 类里通用性强的接缝（storage-postgres 后端、settings 策略层、per-user home）按官方贡献规范提 PR：合入一次，永久受益，冲突面进一步归零。多用户是社区普遍诉求，接受度可期
私有接缝不上游医院特有部分（4A 对接、科室租户模型）留在树外仓库——避免为合并而泄漏业务设计
新增风险 R11（官方破坏性升级）：概率中、影响中——上游大版本重构服务契约（如 agent-loop 换血）时，A 类插件需要集中适配。对策：升级工作流第 3 步的契约检查前置暴露 + 允许锁老版本一版缓冲 + 关键接缝持续向上游 PR 化解。等级：中（有明确信号、有缓冲手段、不阻塞业务；见 19.3 升级工作流）。
