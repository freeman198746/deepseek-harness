AIMS-DSH 多租户对接方案

AIMS 侧规划 身份与授权对接 工作空间生命周期编排 患者级工作空间 就诊级会话 等保合规

AIMS 医生站如何作为第一个多租户宿主（Host）接入 DSH 多用户改造（dsh-multiuser）。本文档是《DeepSeek-Harness-多用户租户改造方案.html》（DSH 侧，编写中）的镜像篇与唯一对接配套：DSH 侧定"租户引擎怎么造"，本方案定"AIMS 这个宿主怎么接"，两侧方案一一对应、互为镜像。既有"患者维度会话隔离"诉求已并入本方案统一设计（见 11.2）。
核心场景（龙哥 2026-09-06 提出）：① 用户（医生）自动创建主工作空间；② 按患者自动创建患者级工作空间；③ 单次就诊自动创建会话。本文为评审迭代稿 v0.4：6 个决策点已全部拍板——① C 模型（首诊 owner 私有 + 主动共享）、② b 立即建会话、③ a 只归档不删、④ a 医院=租户、⑤ a mock 桩先行、⑥ a 三前缀命名空间（见 12.2）。

〇、结论先行

可行，且 AIMS 侧改动收敛在"一个服务端模块 + 协议 v2 扩展"。关键设计转向（v2026-09-06 增）：AIMS 侧不再建立三张映射表，所有 AIMS↔DSH 实体对应关系由 DSH 侧 biz_key 反查族承担（DSH 方案 #17 host/lookup），AIMS 只在内存中缓存当前会话需要的 (workspaceId, sessionId, dshUserId) 三元组，零持久化映射。对接的本质是一次职责切分：

维度结论
AIMS 的角色身份源（IdP）+ 生命周期编排器（provisioning）+ 业务上下文推送方。不承载 DSH 的租户数据（会话/技能/资产/记忆全在 DSH）。
身份对接走 DSH 多租户方案第六节已规划的「宿主嵌入」渠道：AIMS 服务端持机器渠道 API Key，为登录医生换发短期用户 JWT（uid/tid 声明），iframe 面板凭 JWT 打 apiproxy。既有固定 token 面板链路降级为运维兼容模式（演进表见 2.4）。
三个自动创建全部走 AIMS 服务端 → DSH 机器渠道 provisioning API（ensure 语义 + 业务键幂等），不走 postMessage（绕过服务端审计）。postMessage 协议 v2 只负责视图切换与上下文注入。
患者工作空间首诊医生 owner 私有（v0.3 拍板）：首诊医生 = owner，默认仅 owner 可见可写；owner 可主动邀请其他医生加 member（成员授予 API）。急诊医生/转科会诊走"申请-准入"流（owner 审批后加 member）。本阶段不做 workspace 转让（预留 API 不实现）；不做一次性授权链接、按角色模板、跨院区 share（DSH Phase 2 再议）。对齐 DSH workspace + workspace_member。
AIMS 侧数据零映射表（v2026-09-06 设计转向）。所有 AIMS 业务键 → DSH 内部 id 的对应关系走 DSH 侧 (tenant_id, biz_key) UNIQUE 索引 + GET /mu/v1/lookup 反查族（DSH 方案 #17）。AIMS 仅在请求作用域内存中缓存 (workspaceId, sessionId, dshUserId) 三元组；进程重启即丢，下次请求重查。患者正文、上下文快照、产物全部落 DSH 用户桶 + DSH 元数据库，AIMS 侧唯一真相源 = AIMS 业务表本身（userCode/cureno/visitId）。
前置依赖DSH 多租户改造第一阶段（apiproxy 强制认证 + biz_key 列 + UNIQUE 索引 + ensure/lookup API）必须先行；本方案第九节的 API 契约清单需回灌进 DSH 方案，作为其「宿主嵌入渠道」的具体化。

一、对接定位与职责边界

1.1 总原则

  1. 单一职责切分：AIMS 管"谁在用、为了哪个患者哪次就诊用"，DSH 管"会话、技能、资产、记忆怎么存怎么隔"。
  2. 幂等优先：所有 provisioning 都是 ensure 语义（存在即复用，不存在即创建），幂等键 = AIMS 侧业务键（usercode / cureno / visitId），重复触发零副作用——医生反复开关 uAI tab、多端并发进入同一患者，都不能产生重复工作空间。
  3. 控制面与数据面分层：创建/授权等写操作走服务端 API（机器渠道，带审计）；iframe 内的 postMessage 只做视图切换（切工作空间、切会话）和上下文注入（患者快照）。
  4. 隐私最小化：进 DSH 的患者信息只取"AI 辅助诊疗所需最小集"，且明确标注脱敏与禁入域（见第十节）。
  5. 降级可用：DSH 不可达时 uAI tab 显示可重试的占位面板，不影响 AIMS 主流程（患者诊疗操作零耦合）。

1.2 职责矩阵

能力AIMS（宿主）DSH（租户引擎）
医生身份认证源：医院 4A / 域账号登录，产出 usercode + 科室消费方：验 JWT / 查 mu_user
租户与用户记录触发 ensure（首登/首开 uAI）承载：mu_tenant / mu_user，RLS 兜底
工作空间生命周期编排：按业务事件触发 ensure / 归档承载：mu_workspace + 成员表 + 用户桶目录
会话创建与归属提供业务键（visitId）与命名建议承载：mu_session，lineage 血缘
患者临床数据源：HIS/EMR 视图，负责快照组装 + 脱敏只收快照（会话上下文），不回写
AI 会话/技能/资产/记忆不感知内容承载：用户桶 + mu_* 元数据
业务 ↔ DSH 实体定位不存：AIMS 业务键（userCode / cureno / visitId）→ DSH 内部 id 完全交给 DSH 侧 biz_key 反查族（UNIQUE (tenant_id, biz_key) 索引 + GET /mu/v1/lookup）承载：app_user / workspace / session_meta 三表的 biz_key 列 + UNIQUE 索引 + lookup API（DSH 方案 #17/#18）

审计业务侧审计（谁在何时对哪个患者开了 AI）mu_audit 四元组 (tenantId, userId, sessionId, traceId)
为什么 AIMS 侧不放映射表（v2026-09-06 设计转向）？① 单一真相源原则：DSH 是租户引擎，biz_key 反查是其内禀能力（UNIQUE (tenant_id, biz_key) 索引就是干这个的），AIMS 再造一份是冗余且需对账；② 状态一致性：AIMS 侧映射若存在，状态变更要双向同步（出院要同时改 AIMS 映射 status + 调 DSH archive），零映射则只需调 DSH 一处；③ 跨域优雅：AIMS 业务表本身就是 userCode/cureno/visitId 的 source of truth，根本不需要"另一份"来查"是不是已建过 DSH 实体"——直接 lookup DSH 即可。代价：AIMS 每次面板渲染都要先打一次 lookup（DSH 索引 UNIQUE 是 O(1) 命中，毫秒级，可接受）。

二、身份与授权对接

2.1 渠道定位（对齐 DSH 方案第六节矩阵）

DSH 多租户方案的「接入渠道 × 授权方式矩阵」已为本场景预留了行：宿主嵌入（uai-widget / AIMS）→ 宿主服务端换发的短期用户 Token（JWT，带 uid/tid 声明）→ 面板 iframe 请求携带 Token 打 apiproxy。本方案就是把这一行落地。

2.2 换发链路（端到端）

医生登录 AIMS（医院 4A / 域账号）
   │  AIMS 会话建立（usercode、姓名、科室 → tenantKey 映射；科室仅作人员识别，不作权限边界——v0.3 决策点 ①）
   ▼
医生打开 uAI tab（或全局壳首次唤起）
   │  ① 前端调 AIMS 服务端  GET /api/dsh/panel-context?cureno=..&visitId=..
   ▼
AIMS 服务端 DshProvisioningService（机器渠道，持 API Key）
   │  ② ensure 链（幂等，见第三节）：tenant → user → 患者工作空间 → 就诊会话
   │  ③ 调 DSH  POST /mu/v1/auth/token:issue  为该医生换发短期 JWT（30~120min）
   │  ④ 组装返回：{ panelUrl, dshUserId, workspaceId, sessionId, tokenExp }
   ▼
前端 patient-uai-tab 挂 iframe
   │  panelUrl = UaiPanelUrl 模板 + ?token=<JWT>（替换现有 {1}{2} 占位符方案）
   ▼
DSH apiproxy 强制认证中间件
   │  ⑤ 解析 JWT → userId/tenantId → ctx.isolate() → 会话/技能/存储按用户实例化
   ▼
dsh-aims-bridge 插件（iframe 内）
   │  ⑥ aims-ready 上行 → AIMS 下发 aims-open-ctx { workspaceId, sessionId, 患者快照 }
   ▼
DSH 面板切到目标工作空间/会话，注入患者上下文（at-file / 系统提示前缀）

2.3 Token 三层体系

凭证形态生命周期持有方 / 用途
机器渠道 API Key长随机串，作用域 = 租户 + provisioning/token:issue 权限 + 路径白名单（对齐 DSH 方案 mu_user.auth_type='apikey'）长期，可轮换仅 AIMS 服务端（配置中心/密钥库），绝不进前端
用户 JWT短期 JWT，claims = uid / tid / scope=web-panel30~120 分钟iframe URL 一次性携带 → DSH 换 HttpOnly cookie（30 天，按用户）
DSH 面板 cookieHttpOnly; SameSite=Strict30 天DSH 侧会话态；JWT 过期后靠 cookie 续期，bridge 检测 401 才请求 AIMS 重换
过期与续期：JWT 过期 ≠ 面板掉线（cookie 还在）。仅在 cookie 失效（DSH 重启 / 30 天 / 换医生登录）时，bridge 上行 aims-auth-expired，AIMS 前端重新走 2.2 链路。医生站切换登录账号时 AIMS 前端必须销毁并重建 iframe（防上一位医生的 cookie 残留），patient-uai-tab 的"切走即销毁 iframe"现状恰好是正确行为。

2.4 与既有固定 token 面板链路的演进关系

阶段形态说明
现状（已落地）UaiPanelUrl?token=固定值&usercode={1}&cureno={2}单机/单人验证期方案；usercode/cureno 走 URL 明文，DSH 侧无身份语义

2.5 租户键设计（AIMS 组织架构 → mu_tenant）

租户粒度决策：医院（单院区部署）为租户，科室仅作人员识别（v0.3 决策点 ① 修订：不作共享边界）。理由：DSH 的 tenant 承载全局技能/记忆库/配额/加密密钥——以医院为粒度利于统一技能库；科室协作通过 owner 主动成员授予实现（决策点 ① 拍板方案 C），不需要科室级租户。多院区集团化部署时再引入院区维度（tenantKey 加院区前缀即可）。

tenantKey 命名：hospital.<院区代码>      如 hospital.dezhen
userKey   命名：aims.<usercode>           如 aims.D2024001
bizKey    命名：patient.<cureno> / visit.<visitId>   （幂等键，第三节）

三、三个"自动创建"：生命周期编排

3.1 总览：一条 ensure 链

ensureTenant(tenantKey)                          ← 首次部署/新院区，一次
   └─ ensureUser(tenantKey, userKey)             ← 医生首次登录 AIMS / 首开 uAI（幂等）
        └─ ensureUserMainWorkspace(userKey)      ← 用户主工作空间（幂等，默认私有）
ensurePatientWorkspace(tenantKey, cureno)        ← 首次对该患者使用 AI（幂等，owner 私有）
   └─ ensureVisitSession(cureno, visitId)        ← 每次就诊会话（幂等，挂在患者工作空间）
   └─ grantWorkspaceMember(ws, 首诊医生, owner)   ← 首诊医生自动成 owner
整条链在任何一步已存在时直接短路返回已有实体——ensure 是"读多写少"：稳态下 90% 调用只命中 DSH 侧 UNIQUE (tenant_id, biz_key) 索引（毫秒级，不产生 DSH 写流量）。

3.2 用户主工作空间（医生维度的"大本营"）

项设计
触发时机医生首次打开 uAI tab 或全局壳（懒开通，不在登录时批量做——避免 DSH 不可用时阻断登录）；也可由管理员后台预开通
ensure 内容tenant（一次）+ app_user + 主工作空间（display_name = "工作台 · {姓名}"，privacy=private）
用途定位与患者无关的个人会话（科研问答、通用咨询、个人技能试跑）；患者相关会话不落主工作空间（隐私边界清晰）
幂等键userKey（UNIQUE(tenant_id, username) 由 DSH 侧保证）
失败降级ensure 失败 → uAI tab 显示"智能体服务初始化失败 [重试]"占位（不做静默降级，避免医生误以为无此功能）

3.3 患者级工作空间（cureno 维度）

项设计
触发时机医生选中患者后打开 uAI tab（即现有 patient-uai-tab 的使用路径，零新增操作）；危急值推送场景由 notification-hub 主动触发（场景 S6）
ensure 内容workspace（privacy=private，display_name = "{床号}·{姓名}·{cureno 后4位}"，bizKey=patient.{cureno}，v0.3 决策点 ① 拍板 owner 私有）+ 触发医生授予 owner（成员策略见第四节）
患者上下文创建成功后 AIMS 组装患者快照（诊断、过敏史、当前医嘱、检验危急值等最小集，第十节）→ 经 at-file / 系统提示前缀注入会话，快照本体存 DSH 会话上下文，不进 mu_memory
幂等键patient.{cureno} + tenantKey
复诊衔接同一 cureno 再次住院（同院区）复用同一工作空间——就诊历史按会话沉淀在同一空间内，跨就诊连续性天然成立
出院处理状态机：active → archived（出院触发或 T+1 批任务）；archived 后工作空间只读，新就诊会话需重新激活（决策点 ③）

3.4 就诊级会话（visit 维度）

项设计
触发时机立即创建（v0.4 决策点 ② 拍板 b）：医生选中患者 + 进入 uAI tab 的同一原子事务里同步 ensure 就诊会话，与患者工作空间 ensure 同链；备选 a 懒创建（首轮对话才建）已排除——理由：① 时序与工作空间保持一致可减少一次往返；② 状态机起点明确，避免空会话判断；④ v0.4 评审会上"立即建 + 后续未发消息由 DSH GC 回收"的方案胜出（回收策略见 DSH §十四测试章节）
ensure 内容mu_session（挂患者工作空间，title = "{就诊类型}·{yyyy-MM-dd}"，bizKey=visit.{visitId}）
多次对话同一 visit 默认延续同一会话（resume 语义，DSH 原生能力）；医生可手动"新开会话"（同 visit 下多会话并列，lineage 记录）
跨就诊回顾uAI tab 内展示该患者工作空间的会话列表（历史会话模块，DSH 十三章），点击切换 / fork 续聊
幂等键visit.{visitId}；visitId 用 AIMS 就诊流水（挂号/入院事件产生），保证同一次就诊全局唯一

3.5 生命周期状态机（AIMS 侧视角）

[用户]      未开通 ──ensure──▶ active ──────────▶ disabled（离职/停用，成员表移除，数据保留）
[患者空间]  未开通 ──ensure──▶ active ──出院──▶ archived ──再住院──▶ active（复用，会话追加）
[就诊会话]  未创建 ──ensure──▶ active ──就诊结束（出院结算）──▶ closed（只读，可 fork）
[状态机]    AIMS 仅翻译为 DSH 状态字段（workspace.status/privacy、session_meta.status）；archived/closed 只调 DSH 归档/关闭 API
归档 ≠ 删除：医疗数据保存年限（病历级 ≥15 年，等保/电子病历评级要求）下，v0.4 决策点 ③ 拍板 a：只归档不删。DSH 侧 workspace.status = 'archived' / session_meta.status = 'closed'，数据原地保留；后续如需匿名化/物理删除走独立法务评审（不在本方案范围）。

四、患者工作空间归属设计（决策点 ①）

维度方案 A：医生私有（每医生 × 每患者一空间）方案 B：租户共享（每患者一空间，科室成员可见）方案 C：首诊 owner 私有 + 主动共享（v0.3 拍板）
空间数量科内 20 医生 × 在管 200 患者 = 4000 空间/月，膨胀快200 空间/月，与患者数同阶200 空间/月（每患者一空间，owner 私有）
团队协作✘ 主任看住院医的 AI 分析要靠 share/fork，操作链长✔ 接诊医生 writer、科室成员 reader，天然对齐 workspace_member，查房/交班/多学科直接续看◐ owner 主动加 member；协作需 owner 邀请（急诊医生走申请-准入），但权限边界清晰
跨就诊连续性同一患者不同医生各开各的，上下文割裂同一患者全部就诊会话沉淀一处同一患者全部就诊会话沉淀一处（owner 邀请的成员共享上下文）
隐私面较小（只有经治医生可见）较大（科室可见）→ 必须 RLS + 审计 + reader 仅本租户成员最小（默认仅 owner；成员由 owner 显式邀请，全程审计可追溯）
权限控制粒度天然按人隔离可细化：writer 仅主治/接诊登记医生，reader 科室默认；敏感患者（VIP/传染病）可标记 private 单独走方案 A由 owner 完全决定；隐私患者天然满足（无需降级开关）；跨医生访问必须 owner 显式行为
转科/换主治流程新医生建新空间（旧数据不可见）零成本（自动可见）原 owner 邀请新医生；或原 owner 撤销后新医生接诊时走"申请-准入"
急诊/值班场景看不到患者历史直接可见（越权风险）急诊医生发现无 workspace → 走"申请-准入"流，owner 收到申请后决定加 member
离职/调岗owner 走人即数据孤儿其他医生继续可见owner 走人 → workspace 仍存；后续接诊医生走"申请-准入"；本阶段不做转让（预留 API）
推荐方案 C（v0.3 拍板），对齐临床"我的患者我做主"的工作习惯。共享路径单一（仅成员授予 API），权限模型最简；隐私患者天然满足（无须降级开关）。代价：协作需要 owner 主动行为——通过 UI 引导（owner 邀请按钮 + 急诊申请通知）解决。

六、AIMS 侧零映射表（v2026-09-06 设计转向）

6.1 设计依据

结论先行：AIMS 侧不建立任何"业务键 ↔ DSH 内部 id"持久化映射表。所有对应关系由 DSH 侧承担：

实体AIMS 业务键DSH 表 + 业务键列DSH 唯一索引反查入口
医生userCode（如 D2024001）app_user.biz_key = aims.{userCode}UNIQUE (tenant_id, biz_key)GET /mu/v1/lookup?type=user&biz_key=aims.D2024001
患者cureno（如 CURE123）workspace.biz_key = patient.{cureno}UNIQUE (tenant_id, biz_key)GET /mu/v1/lookup?type=workspace&biz_key=patient.CURE123
就诊visitId（如 V20260906001）session_meta.biz_key = visit.{visitId}UNIQUE (tenant_id, biz_key)GET /mu/v1/lookup?type=session&biz_key=visit.V20260906001
三前缀命名空间约定（与 DSH 方案第十六节同步）：aims.*（AIMS 内部主键）、patient.*（患者）、visit.*（就诊）—— 强制隔离避免 AIMS 自增 ID 跟 cureno/visitId 撞 namespace。DSH 不解析 biz_key 语义，仅存储与索引。

6.2 读路径缓存策略（仅请求作用域内存缓存）

panel-context 请求处理顺序：

  1. 查当前请求作用域的内存缓存（ConcurrentDictionary，TTL=请求结束）：若 (workspaceId, sessionId, dshUserId) 全部命中 → 跳过 lookup + ensure，仅需 token 缓存命中即可秒回；
  2. 任一未命中 → 调 DshLookupService 走 GET /mu/v1/lookup，DSH 按 UNIQUE (tenant_id, biz_key) 索引返回内部 id；
  3. lookup 返回 NotFound → 调对应 ensure 族（POST /mu/v1/ensure/{type}）做幂等创建/查找；
  4. 缓存命中但 DSH 调用失败 → 清缓存重试一次（自愈，不持久化所以无需清理）；
为什么不做跨请求持久化？① AIMS 服务端进程重启 = 缓存自然失效，零维护成本；② DSH 是唯一真相源，持久化 AIMS 缓存 = 引入第二份状态（要双向同步/对账）；③ token:issue 每次开 tab 都重新换发（短 TTL），entity id 在请求内就够用。
